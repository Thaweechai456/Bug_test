P0: Workshop: จาก Developer สู่ Tester
P1: อ่าน → คิด → ทดลอง → ค้นหา Bug → พิสูจน์ผล
P2: 🎯 Mission ของ Workshop
P3: สวมบทบาทเป็น Developer เพื่อเข้าใจระบบ แล้วเปลี่ยนเป็น Tester เพื่อค้นหาข้อผิดพลาดจากการทดลองจริงและมีหลักฐาน
P4: จำให้ขึ้นใจ: Developer = สร้าง → Tester = พิสูจน์ → QA = สร้างความมั่นใจในคุณภาพ
P5: Part 1: 👨‍💻 Developer — เข้าใจสิ่งที่สร้าง
P6: อ่าน Source Code / Requirements ของเว็บไซต์ที่นักศึกษาสร้างขึ้น แล้วตอบคำถาม
P11: 1.1 นำภาพหน้าเว็บไซต์ของนักศึกษาใส่ไว้ที่นี่
P13: 1.2 ส่วนของระบบที่คุณศึกษา มีหน้าที่อะไร?
P14: ระบบเป็นแบบฟอร์มลงทะเบียนโปรแกรมเมอร์ สำหรับรับข้อมูลผู้สมัครและตรวจสอบความถูกต้องก่อนส่งใบสมัคร
P15: 1.3 ระบบรับข้อมูลอะไรจากผู้ใช้?
P16: ชื่อ-นามสกุล, อีเมล, เบอร์โทรศัพท์, วันเกิด, ประสบการณ์, ตำแหน่งงาน, เงินเดือน, รูปแบบงาน, ช่องทางติดต่อ, เอกสารแนบ, ข้อความเพิ่มเติม และการยอมรับเงื่อนไข
P17: 1.4 ข้อมูลนั้นมีเงื่อนไขหรือข้อกำหนดอะไร?
P18: ข้อมูลที่มี * เป็นข้อมูลบังคับ; อีเมลต้องมีรูปแบบอีเมล; เบอร์โทรศัพท์ไทยควรมี 10 หลัก; เอกสารต้องเป็น PDF/JPG/PNG ขนาดไม่เกิน 10MB; ต้องยอมรับ Terms & Conditions
P19: 1.5 ถ้าผู้ใช้กรอกข้อมูลถูกต้อง ระบบควรทำอะไร?
P20: เมื่อข้อมูลครบและถูกต้อง ระบบควรอนุญาตให้ส่งใบสมัครและแสดงผลสำเร็จ
P21: 1.6 ถ้าผู้ใช้กรอกข้อมูลผิด ระบบควรทำอะไร?
P22: ระบบควรแจ้งข้อผิดพลาดใกล้ฟิลด์ที่กรอกผิด และไม่อนุญาตให้ส่งจนกว่าจะแก้ไขข้อมูล
P24: Part 2: 🕵️ Tester — เปลี่ยนวิธีคิด
P25: เปลี่ยนจาก “โปรแกรมทำงานอย่างไร?” เป็น “เราจะพิสูจน์ได้อย่างไรว่าระบบทำงานถูกต้อง?”
P26: 2.1 คุณจะทดสอบส่วนนี้อย่างไร?
P27: ทดสอบทั้งกรณีข้อมูลถูกต้อง ข้อมูลว่าง รูปแบบผิด และค่าขอบเขต โดยคลิกส่งฟอร์มและเปรียบเทียบ Expected Result กับ Actual Result
P28: 2.2 คุณจะใช้ Test Data อะไร?
P29: ใช้ข้อมูลหลัก: ผู้ทดสอบ ระบบ, tester@example.com, 2000-01-15, Junior, QA/Software Tester, 25000, Remote, Email แล้วเปลี่ยนเฉพาะเบอร์โทรศัพท์และ Terms ตามแต่ละกรณี
P30: 2.3 ผลลัพธ์ที่คาดหวังคืออะไร? (Expected Result)
P31: ข้อมูลที่ครบและถูกต้องควรส่งได้; ข้อมูลผิดควรถูกปฏิเสธ; เบอร์ 10 หลักควรผ่าน; ไม่ยอมรับเงื่อนไขควรส่งไม่ได้
P32: 2.4 ผลลัพธ์ที่เกิดขึ้นจริงคืออะไร? (Actual Result)
P33: หลักฐานจากหน้าเว็บระบุว่า regex ของ validatePhone() รับ 9 หลักและปฏิเสธ 10 หลัก ส่วน validateTerms() มี bypass ทำให้ไม่ติ๊ก Terms ก็ผ่านได้เมื่อข้อมูลอื่นผ่าน
P34: 2.5 คุณจะตัดสิน PASS หรือ FAIL จากอะไร?
P35: PASS เมื่อ Actual Result ตรง Expected Result; FAIL เมื่อระบบยอมรับข้อมูลที่ควรถูกปฏิเสธ หรือปฏิเสธข้อมูลที่ควรผ่าน
P36: Part 3: 🔎 Find the Bug — ค้นหาข้อผิดพลาด
P37: ทดลองระบบจริงอย่างน้อย 5 สถานการณ์ แล้วเลือกปัญหาที่น่าสนใจ 1–2 รายการมาวิเคราะห์
P39: 3.1 พบปัญหาอะไร?
P40: พบ 2 ปัญหา: (1) validatePhone() ตรวจเบอร์ 9 หลักแทน 10 หลัก และ (2) validateTerms() bypass การตรวจ checkbox
P41: 3.2 คุณทำอย่างไรจึงพบปัญหานี้?
P42: กรอกข้อมูลทดสอบตาม Test Data แล้วตรวจผลหลังคลิกส่ง พร้อมเปิดส่วน Bug Spoilers ของหน้าเว็บเพื่อยืนยันตำแหน่งฟังก์ชันและเงื่อนไข
P43: 3.3 Expected Result ของกรณีนี้คืออะไร?
P44: เบอร์โทรศัพท์ไทย 10 หลักควรผ่าน ขณะที่ 9 หลักควรถูกปฏิเสธ; ผู้ใช้ที่ไม่ยอมรับ Terms ไม่ควรส่งฟอร์มได้
P45: 3.4 Actual Result ที่เกิดขึ้นจริงคืออะไร?
P46: ระบบใช้ /^0[0-9]{8}$/ จึงรับ 9 หลักและปฏิเสธ 10 หลัก; Terms ถูก bypass ด้วย isBypassValidation = true
P47: 3.5 มีหลักฐานอะไร เช่น Screenshot / ข้อมูลที่ใช้ทดสอบ?
P48: Evidence: หน้า https://thaweechai456.github.io/Bug_test/ ส่วน Bug Spoilers; [แทรก Screenshot ของข้อความ Bug Spoiler และผลที่ฟอร์มแสดง]
P50: Part 4: 🐞 Bug Report — รายงานให้คนอื่นเข้าใจ
P51: เลือก Bug 1 รายการ แล้วเขียนรายงานให้ Developer สามารถทำตามและตรวจสอบซ้ำได้
P53: Part 5: 🔁 Re-test — ทดสอบซ้ำหลังแก้ไข
P54: 5.1 หลังจาก Developer แก้ไข คุณทดสอบกรณีเดิมอีกครั้งหรือไม่?
P55: ยังไม่มีเวอร์ชันหลังแก้ไขให้ทดสอบ จึงยังไม่ได้ Re-test จริง
P56: 5.2 ผลการทดสอบเป็น PASS หรือ FAIL?
P57: ผล Re-test: รอดำเนินการเมื่อได้รับ build ที่แก้ไขแล้ว
P58: 5.3 เพราะเหตุใดจึงสรุปผลเช่นนั้น?
P59: หลังแก้ไขให้ทดสอบ Test Data เดิม: 9 หลักต้องไม่ผ่าน, 10 หลักต้องผ่าน, และไม่ติ๊ก Terms ต้องส่งไม่ได้
P60: แนบ Screenshot ของผลหลังแก้ไขเป็นหลักฐานก่อนสรุป PASS/FAIL
P62: Part 6: 💡 Reflection — จาก Developer สู่ Tester
P63: 6.1 วันนี้คุณเรียนรู้อะไรเกี่ยวกับ Software Testing?
P64: ได้เรียนรู้ว่าการทดสอบต้องพิสูจน์ด้วย Expected/Actual และหลักฐาน ไม่ใช่ตรวจเฉพาะกรณีที่ระบบทำงานปกติ
P65: การเลือกข้อมูล boundary และ invalid ทำให้พบความผิดพลาดที่ happy path อาจไม่พบ
P66: 6.2 Developer กับ Tester ต้องคิดต่างกันอย่างไร?
P67: Developer มองการสร้างฟังก์ชันให้ทำงาน ส่วน Tester มองข้อกำหนด ค่าขอบเขต และความเสี่ยงที่ผู้ใช้อาจกรอกผิด
P68: ทั้งสองบทบาทต้องสื่อสารผลที่ตรวจซ้ำได้ด้วย Test Data และหลักฐานเดียวกัน
P69: 6.3 ทำไม Tester ต้องคิดถึงกรณีที่ผู้ใช้กรอกข้อมูลผิด?
P70: เพราะผู้ใช้จริงกรอกผิดได้ และการรับข้อมูลผิดอาจทำให้ข้อมูลไม่ถูกต้องหรือระบบไม่น่าเชื่อถือ
P71: การทดสอบกรณีผิดช่วยป้องกันปัญหาก่อนระบบถูกใช้งานจริง
P72: 6.4 สิ่งที่ยากที่สุดในการหา Bug วันนี้คืออะไร?
P73: ยากที่สุดคือยืนยันว่า Expected Result คืออะไรและเก็บหลักฐานให้ผู้อื่นทำซ้ำได้
P74: การเปิดดู Source/ Bug Spoiler ช่วยยืนยันว่าเป็น defect ไม่ใช่เพียงความเข้าใจผิด
P75: ✅ Checklist ก่อนส่งงาน
P76: ☐ ฉันอธิบายการทำงานของส่วนที่ได้รับมอบหมายได้
P77: ☐ ฉันสร้าง Test Data และ Expected Result ได้
P78: ☐ ฉันทดลองระบบจริงและบันทึก Actual Result
P79: ☐ ฉันพบ Bug และมีหลักฐาน
P80: ☐ ฉันเขียน Bug Report ให้ผู้อื่นทำตามได้
P81: ☐ ฉัน Re-test และสรุป PASS / FAIL ได้
